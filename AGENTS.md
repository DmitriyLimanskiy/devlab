## Текущий интерфейс шаблона

Обновлено 29 октября 2026: DevLab — сервис курсов по разным технологиям. Главная `/` представляет проект целиком, `/courses` показывает стартовый каталог из API. Git-песочница — одно из направлений дальнейшего развития, а не название всего сервиса. Курсы шаблона отмечены «В разработке»; учебные материалы пока отсутствуют. Описанный ниже Git MVP остаётся концепцией будущего направления.

## Идея продукта

DevLab — платформа для изучения IT через эксперименты и визуализацию состояния настоящих инструментов. Первый продукт — Git-песочница: пользователь работает с установленным Git на своём компьютере, а браузер показывает состояние репозитория.

В текущем MVP рассматриваем только свободную песочницу. Уроки, задания и проверка учебного прогресса относятся к дальнейшему развитию.

## Состав MVP

- Локальная CLI на Python, запускаемая командой `devlab`.
- Выбор папки проекта внутри CLI и подключение к сессии песочницы.
- Настоящая интерактивная оболочка внутри CLI через псевдотерминал (PTY).
- Работа с установленным Git: обычные и составные команды, интерактивный ввод и редакторы средствами поддерживаемой оболочки.
- Чтение состояния локального репозитория и синхронизация после завершения команд.
- Наблюдение за внешними изменениями файлов, например из IDE, и периодическая сверка состояния.
- FastAPI для сессий, приёма снимков и уведомления браузера.
- Nginx как публичная точка входа: HTTPS, обратный прокси для API и WebSocket, раздача production-сборки frontend.
- PostgreSQL для сессий и актуального состояния; JSONB для нормализованного снимка.
- React + Vite для визуализации коммитов, веток, тегов, HEAD, рабочих файлов, индекса и конфликтов.
- Один обычный репозиторий и одно активное подключение CLI на сессию.
- Локальная работа при недоступности сервера и повторная синхронизация после восстановления связи.

## Пользовательский сценарий

1. Пользователь запускает `devlab`.
2. В CLI выбирает папку проекта. В папке без репозитория можно выполнить `git init`.
3. CLI связывается с браузерной сессией песочницы и передаёт начальное состояние. Предусматриваем привязку по одноразовому короткоживущему коду; точный порядок экранов и команд подключения ещё нужно спроектировать.
4. CLI запускает интерактивную оболочку в выбранной папке.
5. Пользователь вводит команды. Сначала они выполняются локально, изменяя файлы и `.git`.
6. После завершения команды CLI считывает состояние Git, сравнивает с предыдущим и при изменении отправляет новый снимок на сервер.
7. Backend проверяет данные и версию, сохраняет состояние и уведомляет браузер.
8. Frontend обновляет визуализацию без перезагрузки страницы.

Команды `devlab …` предназначены для управления CLI (например, справка). Полный интерфейс команд и параметров, включая `--help`, проработаем отдельно. Не выдавать обсуждавшиеся примеры команд за реализованный интерфейс.

## Архитектура

```text
Компьютер пользователя
  devlab CLI (Python)
    ├─ выбор папки и привязка сессии
    ├─ оболочка через PTY → установленный Git → файлы и .git
    ├─ интеграция с оболочкой: завершение команды
    ├─ наблюдение за файлами и периодическая сверка
    └─ чтение Git → сравнение → версия снимка → очередь отправки
                             │ HTTPS
                             ▼
                           Nginx
                            ├─ / → статическая сборка React + Vite → браузер
                            ├─ /api/ → FastAPI → PostgreSQL / JSONB
                            └─ /ws/ ↔ FastAPI (WebSocket) ↔ браузер через Nginx
```

CLI инициирует исходящее соединение. Сервер не запускает пользовательские команды, не управляет локальной оболочкой удалённо и не создаёт отдельную среду исполнения для пользователя.

Frontend получает события от FastAPI, а не непосредственно от базы. После открытия или переподключения браузер запрашивает последний снимок через API.

## Ответственность компонентов

### Дизайн системы и Nginx

Система состоит из пяти основных компонентов: CLI, frontend, Nginx, backend и DB. CLI и браузер работают на компьютере пользователя; Nginx, FastAPI и PostgreSQL — на серверной стороне. Это логические компоненты, а не требование отдельных машин или контейнеров.

Nginx — единая публичная точка входа с HTTPS и WSS. Он раздаёт статические файлы production-сборки React + Vite и проксирует запросы API и соединения WebSocket в FastAPI. Для API предварительно используем `/api/`, для WebSocket — `/ws/`, для frontend — `/`; точные пути закрепим при реализации. Frontend работает в браузере; отдельный Node-сервер для production не требуется. Vite используется для разработки и сборки.

Поток сохранения: CLI → Nginx → FastAPI → PostgreSQL. Поток уведомления: FastAPI → Nginx → браузер по WebSocket. Первичное получение состояния и восстановление после переподключения идут через HTTP API по тому же публичному адресу. Nginx передаёт ответы и события в рамках соединений, установленных клиентами.

PostgreSQL доступен backend по внутреннему соединению. CLI и frontend не подключаются к DB напрямую; публичный доступ к backend идёт через Nginx. Конфигурация прокси должна поддерживать WebSocket Upgrade и подходящие таймауты. Конкретные значения, домен, сертификаты и схема запуска предстоит определить.

Для MVP достаточно одного backend-приложения без распределённой шины событий. Масштабирование backend на несколько процессов/реплик и доставка событий между ними требуют отдельного решения; не считать, что внутрипроцессная рассылка работает между всеми репликами автоматически.

### CLI

Разделять управление CLI, терминальную сессию, чтение Git, отслеживание изменений и синхронизацию. Это части одного локального приложения; отдельный установленный агент для MVP не требуется.

PTY отвечает за терминальный ввод и вывод, но сам по себе не определяет завершение команд. Для этого нужна интеграция с выбранной оболочкой. Первая поддерживаемая оболочка и ОС ещё не выбраны; не обещать универсальную совместимость.

Не писать собственный интерпретатор shell и не реализовывать алгоритмы Git с нуля. Команды исполняет настоящая оболочка, Git-операции — установленный Git. Внутренние запросы состояния выполнять с явным списком аргументов, не подставляя данные в shell-строки.

Проверять состояние после завершения команды даже при ненулевом коде возврата: неудачный merge может оставить конфликты. Команда без изменений состояния не требует повторной отправки того же снимка.

Наблюдение за файлами дополняет события оболочки: изменения могут происходить в IDE или другом процессе. Уведомления файловой системы — сигнал перечитать Git, а не описание выполненной операции. Объединять близкие события; при конкурентных изменениях повторять чтение. Не вмешиваться в пользовательские Git-операции ради синхронизации.

### Backend

Управляет сессиями, привязкой CLI, проверкой снимков, их сохранением и доставкой обновлений. Не содержит движок исполнения Git и учебную проверку заданий в MVP.

Повторные запросы должны быть безопасны. Старые версии не могут перезаписать новые. Нужны идентификатор сессии, поколение подключения и монотонный номер версии внутри поколения либо эквивалентный механизм. Подключение нового CLI не должно приводить к конфликту версий старого подключения.

### Frontend

Строит визуализацию из нормализованного состояния. Не вычисляет заново семантику Git-команд. Показывает состояние подключения, время последнего обновления и явно обозначает неподдерживаемые сущности.

Выполнение любой команды установленного Git не означает наличие отдельной анимации или объяснения для неё. Базовая визуализация отражает результат операции.

## Данные и источник истины

Источник истины — локальный репозиторий: рабочие файлы и `.git`. Сервер хранит последнее полученное представление, которое может временно отставать от локального состояния.

Git хранит не JSON и не один файл: объекты, ссылки, индекс и служебное состояние находятся в `.git`, рабочие файлы — рядом с ним. Статус вычисляется сравнением рабочего дерева, индекса и текущего коммита.

Нормализованный снимок для сервера включает:

- Идентификатор сессии, поколение подключения, номер версии и время получения/формирования.
- Коммиты: идентификаторы, родители и необходимые для отображения метаданные.
- Ссылки веток и тегов; HEAD с различением текущей ветки, detached HEAD и отсутствия первого коммита.
- Статусы рабочих файлов и индекса, конфликтующие пути и признаки незавершённых операций.

Точный контракт JSON и способ ограничения объёма истории предстоит спроектировать. Содержимое файлов и diff передавать только при явной потребности функции, а не автоматически копировать всю папку.

Снимок для визуализации не является резервной копией репозитория. Одной `.git` недостаточно для восстановления незакоммиченных и неотслеживаемых рабочих файлов. Полное восстановление потребовало бы согласованного снимка всей рабочей папки.

## Синхронизация и поведение при сбоях

- Выполнение команд не зависит от доступности сервера.
- Локально сохранять последнее неподтверждённое состояние и повторять отправку после восстановления связи.
- Для MVP важна доставка актуального состояния; очередь не обязана хранить каждый промежуточный снимок.
- После переподключения согласовать поколение и версии, восстановить актуальный снимок в браузере.
- Наблюдатель и снимки не гарантируют фиксацию каждого кратковременного перехода состояния.
- Архив введённых команд и полного вывода терминала — отдельная будущая возможность; интеграция завершения команд сама по себе не означает такой архив.
- Присланное клиентом состояние подходит для отображения, но не является независимым доказательством выполнения для экзаменов.

## Критерии готовности MVP

Пользователь запускает `devlab`, выбирает папку, подключает песочницу и работает в оболочке внутри CLI. Создание и изменение файла, add/commit, создание ветки и merge отображаются в браузере без перезагрузки. Правки из IDE тоже синхронизируются.

Пустой репозиторий, detached HEAD, конфликт слияния, ошибка команды, потеря сети и переподключение не ломают локальную работу. Устаревшие сообщения не перезаписывают новое состояние. Повторная команда чтения не вызывает отправку неизменившегося снимка.
