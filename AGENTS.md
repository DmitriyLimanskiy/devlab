- `AGENTS.md` — продукт, архитектура, общие ограничения и взаимодействие компонентов.
- `backend/AGENTS.md` — FastAPI, маршруты, модели и будущая серверная синхронизация.
- `frontend/AGENTS.md` — страницы, API-клиент и согласованная компоновка интерфейса. Подробности оформления — `frontend/DESIGN.md`.
- `cli/AGENTS.md` — локальная оболочка, чтение Git, наблюдение и снимки.
- Nginx, Compose и общие документы относятся к корневой зоне. При изменении контракта проверять обе стороны и настройки прокси/healthcheck.

Текущее состояние реализации и временные ограничения описывать в README и `docs/STATUS.md`, а не в AGENTS. Не дублировать подробные инструкции компонентов в корне. При изменении согласованного поведения обновлять соответствующий AGENTS и пользовательскую документацию. Инструкции пользователя имеют приоритет; этот файл не должен отменять новые решения пользователя.

## Идея продукта

DevLab — сервис курсов по разным IT-технологиям с практикой на настоящих инструментах и визуализацией их состояния. Git-песочница — первое направление, а не название всей платформы.

Первый Git MVP — свободная песочница. Уроки, задания, проверка результата и прогресс относятся к дальнейшему развитию. Пользователь работает с установленным Git на своём компьютере; браузер должен показывать состояние репозитория.

## Состав MVP

Целевой состав, не список уже реализованных возможностей:

- Локальная команда `devlab`, выбор папки и привязка к браузерной сессии.
- Настоящая интерактивная оболочка через PTY и установленный Git, включая составные команды, редакторы и интерактивный ввод.
- Чтение коммитов, ссылок, HEAD, рабочих файлов, индекса, конфликтов и незавершённых операций.
- Проверка после команд, наблюдение за внешними изменениями и периодическая сверка.
- FastAPI для сессий, проверки и сохранения снимков, доставки событий браузеру.
- PostgreSQL / JSONB для последнего нормализованного состояния.
- React для визуализации результата операций без перезагрузки.
- Nginx как публичная точка входа: статика, HTTPS, API и WebSocket.
- Один обычный репозиторий и одно активное подключение CLI на сессию.
- Независимость локальной работы от сервера, повторная отправка актуального состояния после восстановления связи.

## Архитектура и источник истины

```text
Компьютер пользователя
  CLI → bash через PTY → установленный Git → рабочие файлы и .git
   └─ чтение Git → сравнение → локальный снимок → будущая очередь отправки
                                                    │ HTTPS
                                                    ▼
                                                  Nginx
                        браузер ← статика /          ├─ /api/ → FastAPI → PostgreSQL
                        браузер ↔ будущие события    └─ /ws/  ↔ FastAPI
```

Источник истины — локальный репозиторий. `state.json` — упрощённое представление для DevLab, а не внутренний формат Git и не резервная копия. Содержимое файлов и diff не передавать без потребности конкретной функции. Серверное состояние может отставать от локального.

CLI инициирует исходящие соединения. Сервер не выполняет пользовательские команды и не управляет локальной оболочкой. CLI и frontend не подключаются к PostgreSQL напрямую. Frontend получает состояние и события через backend, не пересчитывает семантику Git-команд.

PTY передаёт ввод и вывод, а завершение команды определяет интеграция с bash. Не писать собственную оболочку или алгоритмы Git. Внутренние вызовы Git выполнять списком аргументов, без подстановки данных в shell-строки.

## Согласованное направление синхронизации

Пока проектируется однопользовательский прототип, без разработки многопользовательской авторизации:

1. Открытие Git-песочницы в браузере создаёт сессию либо получает активную.
2. CLI получает список направлений через API, выбирает Git и запрашивает активную сессию до выбора папки. Если её нет, предлагает открыть песочницу в браузере.
3. CLI отправляет снимки с ключом сессии и версией. Backend проверяет ключ и данные, сохраняет состояние, подтверждает приём и уведомляет браузер.

Жизненный цикл и версии описаны в docs/practice-sessions.md, степень готовности — в docs/STATUS.md. Ключ CLI хранится только в памяти процесса, отдельно от state.json и окружения bash. Одноразовые коды и полноценная авторизация — возможное дальнейшее развитие, а не обязательный текущий сценарий. Ключ прототипа связывает данные с сессией, не доказывает личность пользователя.

Сетевую отправку отделять от терминала и чтения Git. Выполнение команд не зависит от доступности сервера. Достаточно доставлять последнее актуальное неподтверждённое состояние; архив всех промежуточных переходов не требуется. Повторные запросы должны быть безопасны. Старые снимки и прошлые подключения не могут перезаписывать новые: нужны поколение подключения и монотонная версия либо эквивалентный механизм. Локальный номер версии файла сам по себе недостаточен.

Браузер после открытия/переподключения получает последний снимок по HTTP, затем обновления от FastAPI. Для MVP достаточно одного backend-приложения. Внутрипроцессная рассылка не работает автоматически между репликами; масштабирование требует отдельного решения.

## Инфраструктура

- Nginx раздаёт сборку frontend и проксирует `/api/`, сохраняя путь. В текущей локальной конфигурации доступ по HTTP на loopback:8080; HTTPS/WSS пока не настроены.
- Backend не публикует порт на хост в Compose. Доступ к PostgreSQL ограничивать внутренней сетью и при необходимости loopback-портом для локальной разработки.
- Разделять конфигурации разработки и production. Изменения исходников могут подхватываться через bind mount и reload; зависимости требуют пересборки.
- Проверять согласованность адресов backend, frontend-прокси и healthcheck при изменении маршрутов.
- Не удалять volume PostgreSQL ради пересборки приложения.
- Домены, сертификаты, WebSocket Upgrade и таймауты закрепить при реализации событий.

## Критерии готовности MVP

Создание/изменение файлов, add/commit, ветка и merge отражаются в браузере без перезагрузки; правки IDE тоже синхронизируются. Пустой репозиторий, detached HEAD, конфликт, ошибка команды, потеря сети и переподключение не ломают локальную работу. Устаревшие сообщения не заменяют новое состояние; чтение без изменений не создаёт повторную доставку.

## Дальнейшее развитие и открытые решения

- Контракт сетевого снимка, хранение ключа, поколения, привязка и жизненный цикл сессии.
- HTTP-отправитель, сохранение неподтверждённого состояния, политика повторов и события браузера.
- Библиотека графа, расположение коммитов и метаданные для отображения.
- Распространение CLI, обновления, другие ОС и оболочки. Сейчас поддержка ограничена macOS + bash.
- Уроки, задания, подсказки и прогресс; запись команд/вывода и воспроизведение; полные снимки и восстановление.
- Несколько рабочих деревьев, подмодули, LFS, расширенные удалённые репозитории и другие тренажёры.

Не выдавать эти планы за принятые технологии или готовые функции. Выполнение команды Git не означает отдельной анимации для неё. Клиентский снимок не является независимым доказательством выполнения экзамена.

## Общие правила работы

- Документацию и пояснения писать на русском, технические имена сохранять. Раздел о первой версии называть «Состав MVP».
- Сохранять согласованный объём продукта; расширения обсуждать отдельно.
- Не обещать универсальную поддержку оболочек, ОС и сущностей Git без проверки.
- Не менять пользовательские файлы и Git/shell-настройки без необходимости и согласованного поведения. Создание снимка и дополнение `.gitignore` для него уже согласованы.
- Проверять изменения соразмерно задаче. Терминал, Git и синхронизацию проверять реальными временными репозиториями и сценариями ошибок, не только моками.
- `sources/` содержит исходные материалы и визуальный референс; не удалять. `.venv/` и `.idea/` не определяют архитектуру проекта.
