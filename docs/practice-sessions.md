# Сессии песочницы и версии снимков

Зафиксировано 30 октября 2026 года. Согласованная логика однопользовательского прототипа. Документ описывает целевое поведение; наличие моделей запросов не означает готовность сессий, хранения и доставки снимков.

## Назначение сессии

Сессия связывает браузерную песочницу курса, подключение CLI и последнее полученное состояние локального репозитория. На один курс допускается одна активная сессия в рамках текущего однопользовательского прототипа.

Источник истины — локальные файлы и `.git`. Сервер хранит последнее полученное представление, которое может отставать. Снимок не является резервной копией.

## Идентификаторы и версии

| Поле | Значение | Кто задаёт |
| --- | --- | --- |
| `schema_version` | Версия формата снимка, сейчас `1` | Контракт приложения |
| `session_id` | UUID сессии песочницы | Сервер |
| `generation` | Номер подключения CLI внутри сессии | Сервер |
| `version` | Номер снимка внутри поколения | CLI |
| `state` | Нормализованное состояние Git | CLI |

`generation` не считает снимки и не меняется после Git-команд. При каждом новом подключении CLI сервер увеличивает поколение. До первого подключения сессия ещё не имеет действующего поколения CLI; сетевые снимки используют положительные значения, начиная с `1`.

`version` начинается с `1` в каждом новом поколении и увеличивается при сохранении нового изменившегося состояния. Команда без изменения состояния не создаёт новую версию. Повторная доставка уже сформированного снимка сохраняет его версию и содержимое.

```text
Первое подключение:   generation=1, version=1 → 2 → 3
Перезапуск CLI:       generation=2, version=1 → 2
Повторная отправка:   generation=2, version=2 (без увеличения)
```

Версии не обязаны поступать подряд: очередь может заменить промежуточные снимки последним актуальным. После версии `2` сервер может принять версию `5`.

## Жизненный цикл сессии

Состояния сессии: `active` и `closed`. Подключённость CLI и браузера не является статусом жизненного цикла сессии.

| Событие | Поведение |
| --- | --- |
| Открытие Git-песочницы | Вернуть активную сессию курса; при её отсутствии создать новую |
| Обновление страницы или открытие второй вкладки | Вернуть ту же активную сессию и последний снимок |
| Подключение CLI | Увеличить поколение, выдать новый ключ подключения, начать версии с `1` |
| Выход из CLI | Оставить сессию активной и сохранить последний снимок |
| Потеря сети | Не закрывать сессию и не останавливать локальную оболочку |
| Восстановление связи в том же процессе CLI | Продолжить текущее поколение, если оно ещё действует |
| Перезапуск CLI | Оформить новое подключение и новое поколение |
| Закрытие вкладки браузера | Не закрывать сессию |
| Явное завершение сессии | Перевести в `closed`; запретить новые подключения и запись снимков |
| Открытие песочницы после завершения | Создать новую сессию с новым UUID |

Автоматическое истечение сессии пока не вводится. Срок хранения закрытых сессий и снимков предстоит определить. Закрытие не означает немедленное удаление данных. Heartbeat и таймаут присутствия CLI будут проектироваться отдельно; отсутствие запросов само по себе не доказывает отключение.

## Подключение и ключ

Браузер создаёт или получает сессию курса. CLI получает направления через API, выбирает Git и запрашивает активную сессию до выбора локальной папки. Если сессии нет, CLI предлагает открыть песочницу в браузере. Возможность локальной работы сохраняется.

Новое подключение CLI получает секретный ключ и поколение. Сервер хранит только хеш ключа. Ключ передаётся в заголовке `Authorization: Bearer …`, отдельно от `state`, и не записывается в `state.json`.

Новое поколение заменяет предыдущее подключение: его ключ и запросы больше не могут обновлять состояние. Выдача ключа и увеличение поколения должны происходить атомарно. Простое восстановление сети в действующем процессе не требует выдачи нового поколения.

Ключ однопользовательского прототипа связывает запрос с сессией и подключением, но не подтверждает личность пользователя. Полноценная авторизация и одноразовые коды сейчас не входят в этот этап. Ключ CLI хранится только в памяти процесса. Безопасное автоматическое повторение запроса подключения при потере ответа ещё требует решения и пока отключено.

## Формирование и доставка снимка

1. CLI читает состояние Git после завершения команды, включая ошибку, либо после внешнего изменения/периодической сверки.
2. Сравнивает состояние с предыдущим. Если оно не изменилось, новая версия не создаётся.
3. При изменении сохраняет новый снимок с увеличенной версией и передаёт тот же снимок отдельному отправителю. Не нужно наблюдать за `state.json` ради сети.
4. Отправитель сохраняет последнее неподтверждённое состояние и доставляет его независимо от работы bash.
5. При ошибке повторяет отправку с задержкой. Если появились новые снимки, достаточно доставить последний; архив промежуточных состояний не требуется.
6. Сервер подтверждает приём после успешного сохранения. CLI снимает с ожидания только подтверждённую версию: поздний ответ на старый запрос не подтверждает более новый снимок.

При подключении нового поколения CLI формирует актуальное начальное состояние с сетевой версией `1`, даже если Git не изменился. Это исключение из обычной дедупликации: новое подключение должно передать своё исходное состояние.

Текущий локальный `state.json` имеет собственную версию и режим сохранения существующего файла (`yes/no`). Нельзя просто использовать сохранённый номер как номер нового сетевого поколения. При реализации отправителя необходимо явно согласовать локальную и сетевую нумерацию. Если пользователь выбрал `no`, правило сохранения локального файла до следующего изменения не отменяет начальную передачу актуального состояния новому подключению; не следует молча отправлять устаревшее содержимое файла.

## Правила приёма

Сервер проверяет активность сессии, ключ, действующее поколение, поддерживаемую версию схемы и структуру `state`.

| Ситуация | Результат |
| --- | --- |
| Действующее поколение, версия выше последней принятой в нём | Сохранить снимок и подтвердить |
| Первое состояние нового действующего поколения | Заменить предыдущий снимок, даже если его локальная версия была больше |
| Те же поколение и версия, то же содержимое | Безопасно подтвердить повтор, без замены и повторного события изменения |
| Те же поколение и версия, другое содержимое | Отклонить как конфликт |
| Версия ниже последней принятой в текущем поколении | Не заменять актуальное состояние |
| Прошлое или ещё не выданное поколение | Отклонить |
| Закрытая сессия, неверный ключ или неподдерживаемая схема | Отклонить |

Проверка поколения/версии и запись должны выполняться атомарно, чтобы конкурентные запросы не могли откатить состояние назад. При сравнении содержимого учитывать структуру JSON, а не пробелы и порядок ключей. Точные HTTP-коды и формат подтверждения закрепить при реализации ручек.

## Хранение и браузер

Хранение описано двумя отдельными таблицами (app/db/models/practice.py):

- `practice_sessions`: идентификатор, курс, статус, текущее поколение, данные хеша ключа и даты жизненного цикла.
- `practice_snapshots`: одна последняя запись на сессию, `schema_version`, `generation`, `version`, JSONB `state` и время получения сервером.

При новом подключении предыдущий снимок остаётся доступным до приёма нового. Браузер должен видеть различие между поколением сохранённого снимка и текущим поколением подключения и не выдавать старые данные за свежее состояние нового CLI.

При открытии или переподключении браузер получает последний снимок через HTTP. После успешного сохранения backend уведомляет его по WebSocket. Показываются состояние связи и время обновления. База не отправляет события напрямую в браузер. Для MVP достаточно одной backend-реплики.

## Проверки реализации

- Повторное открытие курса сохраняет активную сессию; явное завершение приводит к созданию новой при следующем открытии.
- Новое подключение увеличивает поколение и лишает старый ключ права записи.
- Потеря сети в том же CLI не увеличивает поколение, если оно остаётся действующим.
- Начальное состояние нового поколения принимается после большей версии предыдущего поколения.
- Команда без изменений не создаёт новую версию; повторная отправка не меняет версию.
- Пропуск промежуточных версий допустим, запоздавшие/конкурентные запросы не откатывают состояние.
- Повтор с тем же содержимым безопасен; повтор с другим содержимым отклоняется.
- Ошибка сохранения не приводит к подтверждению; запоздавший ответ не снимает новый снимок с очереди.
- Новый CLI передаёт актуальное состояние даже при выборе сохранения существующего локального файла.
- Серверная недоступность не блокирует команды и восстановление связи приводит к доставке актуального состояния.

## Текущая ручка открытия курса

POST /api/v1/git-course без тела создаёт или возвращает активную сессию Git и возвращает session_id, generation и steps. Создание выполняется PostgreSQL upsert по частичному уникальному индексу; повторное открытие не обновляет поколение CLI. HTTP-обработчик расположен в app/api/routes/git_course.py, модели ответа — в app/api/schemas/git_course.py.

## Реализованное подключение CLI

CLI получает GET /api/v1/catalog, выбирает курс и отправляет POST /api/v1/cli-connect с course_slug до выбора папки. Ответ содержит session_id, generation и исходный ключ; сервер сохраняет хеш. Отсутствие сессии — 404 с предложением открыть курс. Доступен локальный режим.

После выбора папки CLI заново читает Git и отправляет POST /api/v1/cli-send-snapshot с начальной сетевой версией 1 и Bearer-ключом. Это работает и при no для локального файла: старый файл сохраняется, но отправляется текущее состояние. Локальный номер снимка независим. Подтверждение проверяется по тройке session_id/generation/version.

Начальная и последующие отправки выполняются потоком sync.py после fork PTY, без ожидания сети оболочкой. Наблюдатель передаёт изменившееся состояние напрямую. Ключ не сохраняется в файлах/окружении bash. Очередь сохраняет только последний неподтверждённый снимок, повторы используют прежнюю версию. Временные сетевые ошибки повторяются с задержкой до 30 секунд; постоянные 4xx останавливают доставку до нового явного подключения. При выходе ожидание ограничено, файл очереди остаётся без ключа. Следующий запуск получает новое поколение и заменяет прежнюю очередь актуальным чтением Git с version=1. Получение состояния браузером и WebSocket ещё не реализованы.
