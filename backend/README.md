# DevLab Backend

FastAPI-приложение и миграции PostgreSQL. Запуск API не создаёт таблицы и не применяет миграции автоматически.

## Структура приложения

```text
app/
├── main.py                     # создание FastAPI и подключение роутеров
├── api/
│   ├── routes/
│   │   ├── course_catalog.py   # каталог курсов
│   │   ├── git_course.py       # открытие Git-песочницы
│   │   └── cli.py              # подключение CLI и приём снимков
│   └── schemas/
│       ├── course_catalog.py   # ответ каталога
│       ├── git_course.py       # сессия и шаги курса
│       ├── snapshot.py         # конверт запроса со снимком
│       ├── git_state.py        # содержимое состояния Git
│       └── cli.py              # запрос/ответ подключения CLI
└── db/
    ├── base.py                 # DeclarativeBase и соглашения имён
    ├── config.py               # URL подключения из окружения
    ├── session.py              # AsyncEngine и AsyncSession
    └── models/
        ├── course.py          # courses, course_steps
        └── practice.py        # practice_sessions, practice_snapshots
```

`api/schemas` описывает HTTP-данные, `db/models` — хранение. Alembic импортирует общую Base и регистрирует модели из db/models. Перенос Python-модулей не меняет таблицы и не требует отдельной миграции.

## Контракт страниц и API

| Страница | Метод и API | Ответ |
| --- | --- | --- |
| `/catalog` | `GET /api/v1/catalog` | Список курсов: id=slug, title, description, status, position |
| `/git-course` | `GET /api/v1/git-course` | Список Git-курсов: id=slug, title, description, status, position |
| Выбранная вкладка Git | `POST /api/v1/git-course`, JSON `{"course_slug":"git-sandbox"}` | session_id, generation, steps |

GET Git читает курсы со slug, начинающимся с `git-`, сортирует по position/id и не создаёт сессии. Фиксированного списка названий нет; подписи вкладок берутся из title. POST Git принимает обязательное JSON-тело с course_slug из id выбранного курса, атомарно создаёт или возвращает его активную сессию, затем читает только его шаги по course_id. Поле course_slug — строка длиной до 100 символов с префиксом git-, дополнительные поля запрещены. Сессии вкладок независимы; отсутствие шагов возвращается как steps=[]. Повторное/параллельное открытие не меняет поколение, ключ и даты существующей сессии. Отсутствующий курс возвращает 404, некорректное или отсутствующее тело — 422. Создание подключения CLI и выдача ключа здесь не выполняются.

## Таблицы

SQLAlchemy-модели находятся в `app/db/models/`, отдельно от Pydantic-моделей HTTP в `app/api/schemas/`.

- `courses`: `id` (identity), уникальный `slug`, `title`, `description`, `status`, `position`, `created_at`, `updated_at`.
- `course_steps`: `id` (identity), `course_id`, `slug`, `position`, `title`, `content` (JSONB), `created_at`, `updated_at`.

Все поля обязательны. Позиции положительные, считаются с 1. Статусы курса: `planned`, `available`, `archived`. Названия шагов и наполнение не являются прогрессом пользователя.

Внешний ключ связывает шаг с курсом; удаление курса с шагами запрещено (`RESTRICT`). Внутри курса уникальны позиции и slug шагов. Уникальное ограничение `(course_id, position)` создаёт индекс, пригодный для выборки шагов курса в нужном порядке; отдельный дублирующий индекс не нужен. В запросах явно использовать `ORDER BY position`.

`content` — JSON-объект. Например:

```json
{"blocks": [{"type": "text", "text": "Открой терминал."}, {"type": "code", "language": "bash", "text": "devlab"}]}
```

База проверяет, что это объект. Состав блоков — будущий контракт API, отдельная валидация блоков пока не реализована. При обновлении через ORM присваивать новый объект `content`: вложенные изменения словаря на месте не отслеживаются автоматически.

Даты имеют часовой пояс. `created_at` и начальный `updated_at` задаёт PostgreSQL. Последующие изменения `updated_at` обслуживает SQLAlchemy; для прямых SQL UPDATE значение нужно задавать явно, триггера нет.

## Применение миграции вручную через Docker

Из корня проекта, с настроенным `.env`:

```sh
docker compose up -d postgres
docker compose build backend
```

Дождаться готовности PostgreSQL (`docker compose ps`). Просмотреть SQL без применения:

```sh
docker compose run --rm --no-deps backend alembic upgrade head --sql
```

Применить, когда готов:

```sh
docker compose run --rm --no-deps backend alembic upgrade head
docker compose run --rm --no-deps backend alembic current
```

Миграция `20261030_0001` создаёт только таблицы и ограничения, без курсов и шагов. Каталог API читает таблицу courses через AsyncSession. Наличие подготовленного файла миграции не означает, что он уже применён к твоей базе.

Параметры `POSTGRES_*` передаются backend из Compose. При использовании существующего volume они должны совпадать с учётными данными, с которыми база была создана; изменение `.env` не меняет пароль существующей базы. Секреты не хранятся в `alembic.ini`.

## Локальный Alembic

Из `backend/`:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/alembic upgrade head --sql
```

Для online-команд нужен доступ к PostgreSQL и переменная `DATABASE_URL` вида `postgresql+psycopg://USER:PASSWORD@HOST:5432/DB` либо `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`. В URL специальные символы пароля нужно кодировать; набор `POSTGRES_*` этого не требует. `.env` автоматически не читается локальным Alembic. Compose публикует PostgreSQL на `127.0.0.1:5432`. При локальном запуске задавать POSTGRES_HOST=127.0.0.1; внутри Docker используется postgres.

Будущие изменения моделей оформлять новой ревизией:

```sh
.venv/bin/alembic revision --autogenerate -m "описание изменения"
```

Autogenerate требует доступа к БД; перед применением проверять сгенерированный файл. Уже применённые миграции не редактировать. Downgrade начальной миграции удаляет обе таблицы вместе с данными, поэтому не использовать его для обычного обновления.

Настройка основана на [документации Alembic](https://alembic.sqlalchemy.org/en/latest/tutorial.html) и [PostgreSQL-диалекте SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#psycopg).

## Сессии приложения

`app/db/session.py`: один лениво создаваемый AsyncEngine на процесс, async_sessionmaker и зависимость get_session с async with. Запросы и commit выполняются с await, автоматического commit нет. AsyncSession нельзя разделять между конкурентными задачами. Psycopg 3 используется в асинхронном режиме; URL остаётся postgresql+psycopg. Alembic online использует асинхронное подключение и run_sync для операций миграции.

## Модель входящего снимка

`app/api/schemas/cli/snapshot.py` описывает `SnapshotReq`, `git_state.py` — вложенные модели состояния. Контракт используется ручкой приёма снимков.

В `state` передаётся именно поле `state` локального файла CLI, без обёртки `generator/version/updated_at`. Версия доставки, поколение и сессия находятся на верхнем уровне запроса.

Дискриминатор `kind` выбирает один из трёх форматов:

- `repository`: `path`, `head`, `branch`, `head_kind`, `files`, `refs`, `commits`, `history_limit`, `operations`.
- `no_repository`: выбранная `path` без Git-репозитория.
- `unavailable`: недоступная `path`.

Коммит содержит полный `id` и `parents`; принимаются SHA-1 и SHA-256. Родители могут быть вне ограниченной истории. В текущем контракте предел истории — до 200 коммитов.

Файл содержит `path`, отдельные символы `index` и `worktree` из porcelain, `conflict` и необязательный `original_path`. Пробел в статусе значим. Для переименования/копирования исходный путь обязателен.

`refs` сохраняет формат текущего CLI: строки `refs/heads/main <хеш>` / `refs/tags/v1 <хеш>`. Ссылка тега не обязана указывать непосредственно на коммит. `operations` содержит признаки merge, cherry-pick, revert, rebase и bisect, которые собирает CLI.

Для `unborn` HEAD пустой, ветка указана; для `branch` указаны оба значения; для `detached` есть HEAD без ветки. Неизвестные поля, некорректные хеши и противоречивые состояния отклоняются. Полная семантическая проверка Git и сетевой лимит размера запроса в эти модели не входят.

Проверка моделей на настоящих временных репозиториях:

```sh
PYTHONPATH=backend backend/.venv/bin/python -m unittest discover -s backend/tests -v
```

## Модели сессий песочницы

`app/db/models/practice/practice.py` содержит `PracticeSession` и `PracticeSnapshot`; обе модели зарегистрированы в общей metadata для Alembic. Для этих таблиц добавлена отдельная миграция `8ca2ebb96c2b`; применение выполняется вручную. Начальная миграция курсов не меняется.

- `practice_sessions`: UUID (`uuid4` задаётся Python), курс, статус active/closed, поколение (0 до первого CLI), хеш ключа, время создания/последнего подключения/закрытия. Частичный уникальный индекс разрешает одну active-сессию на курс. `closed_at` обязателен только при closed.
- `practice_current_states`: одна обновляемая запись на сессию: HEAD, ветка, refs, статусы файлов, индекс, операции и SHA коммитов текущего снимка
- `repository_commits`: уникальные коммиты по сессии, repository_id и SHA; родители и первое событие появления
- `practice_graph_events`: контекст репозитория и изменения refs (before/after/целевой коммит тега), без файлов и копии графа
- `practice_snapshot_receipts`: компактные подтверждения с хешем запроса и уникальностью (session_id, generation, version)

Все новые внешние ключи используют RESTRICT: закрытие не означает удаление. Временная разница поколений сессии и последнего снимка допустима. Проверка ключа, принятие только новых версий и атомарная выдача поколения реализованы обработчиками CLI; модели сами этого не обеспечивают.

Жизненный цикл описан в [practice-sessions.md](../docs/practice-sessions.md). Alembic autogenerate требует подключение к текущей БД; выполнять его из окружения с доступом к БД и правом записи в `alembic/versions` (Compose монтирует каталог миграций только для чтения).

## Проверки

Из корня проекта:

```sh
PYTHONPATH=backend backend/.venv/bin/python -m unittest discover -s backend/tests -v
```

Проверки снимков используют временные Git-репозитории. Проверки ручки Git требуют PostgreSQL и включаются явно; они создают и удаляют отдельные временные схемы, не меняя прикладные таблицы:

```sh

```

Проверяются параллельное открытие одной сессии, сохранение поколения, сортировка/принадлежность шагов, создание после закрытой сессии и отсутствие курса. Для локального запуска можно указать `TEST_DATABASE_URL`; по умолчанию берутся обычные переменные подключения. Без RUN_DB_TESTS проверки PostgreSQL пропускаются.

## Подключение CLI и приём снимков

`POST /api/v1/cli/connect` принимает course_slug, находит активную сессию, увеличивает generation, выдаёт новый ключ и сохраняет только SHA-256 ключа. `POST /api/v1/cli/send-snapshot` принимает SnapshotReq и заголовок Authorization: Bearer. Ответ подтверждает session_id, generation и version после commit. Повтор той же версии с тем же содержимым не обновляет received_at; старые версии/поколения и противоречащие повторы отклоняются.

CLI уже использует каталог и обе ручки для подключения и начального снимка. Постоянная фоновая отправка и повторная доставка реализованы в CLI. Реальные запросы подключения и начальной доставки проверены; отдельные интеграционные проверки всех веток приёма (ошибки ключей, версий, поколений, повторы и конкуренция) ещё нужны. Код обработчиков — `app/api/routes/cli/cli.py`, модели — `app/api/schemas/cli/cli.py` и `snapshot.py`.

## Состояние и события браузера

`GET /api/v1/practice-sessions/{session_id}/snapshot` возвращает `session_id`, `status`, текущее `generation`, `connected_at` и `snapshot` (null до первого снимка). Снимок содержит schema_version, session_id, generation, version, state и received_at. Ответ не кешируется, ключи не возвращаются; неизвестная сессия — 404. Поколение снимка может отставать от поколения сессии.

`WS /ws/practice-sessions/{session_id}` проверяет существование сессии, регистрирует подписку, затем отправляет `{"type":"ready"}`. После ready браузер перечитывает HTTP. Сохранение нового снимка и новое подключение CLI после commit отправляют `{"type":"state_changed"}`. Безопасный повтор снимка события не создаёт. Каждые 20 секунд отправляется ping, чтобы соединение не простаивало на прокси. Разрыв требует новой подписки и HTTP-чтения.

Рассылка в `app/services/practice/practice_events.py` работает в одном процессе FastAPI. Для медленного клиента сигналы объединяются в очередь размером 1; данные читаются из БД, история событий не хранится. Несколько workers/реплик требуют общего транспорта событий. Браузерные ручки соответствуют однопользовательскому прототипу, полноценной авторизации нет. WebSocket-транспорт Uvicorn включён зависимостью websockets; при обновлении зависимостей пересобрать backend.

Проверка реальных HTTP/WebSocket и PostgreSQL в отдельной временной схеме: `RUN_DB_TESTS=1 PYTHONPATH=. .venv/bin/python -m unittest discover -s tests -v`. Дополнительно проверяются восстановление после пропущенного события, отсутствие события на повтор и различие поколений.


## Присутствие CLI

POST `/api/v1/cli/heartbeat` и `/api/v1/cli/disconnect` принимают `{session_id, generation}` и Bearer-ключ. Используют ту же проверку активной сессии, ключа и поколения, что приём снимков. Ответ `{session_id, generation, connected}`. Новый connect сбрасывает присутствие прежнего подключения.

Heartbeat поступает каждые 10 секунд, аренда действует 35 секунд по монотонным часам backend. HTTP-состояние дополнено cli_connected и cli_lease_seconds; браузер отсчитывает оставшуюся аренду и сверяет HTTP каждые 10 секунд. Подключение и явное отключение уведомляют браузер; истечение аренды обнаруживается отсчётом/сверкой. Снимок, его версия и время получения при heartbeat не меняются.

Аренда хранится в памяти единственного backend-процесса, после его перезапуска CLI подтверждает присутствие следующим heartbeat. Миграция не требуется. Пропавший CLI не закрывает браузерную сессию. При масштабировании аренду и события нужно вынести в общее хранилище.

## Нормализованная история графа

`POST /api/v1/cli/send-snapshot` сохраняет контракт CLI: schema_version/session_id/generation/version/state. Сервер обновляет текущее состояние; новые коммиты добавляет один раз, изменения refs — отдельными событиями. При git switch без новых refs/коммитов, изменении файла или индекса событие истории не создаётся. На каждую принятую версию остаётся только компактное подтверждение SHA-256 для проверки повторов. Идентичный повтор любой принятой версии действующего поколения подтверждается без обновления состояния; конфликт — 409.

`GET /api/v1/practice-sessions/{session_id}/snapshot` собирает текущее состояние с коммитами и возвращает `graph_history_id` — отдельный курсор истории. ID самого снимка остаётся ID подтверждения доставки. Курсор и метаданные текущего состояния читаются согласованно одним SELECT; родители подтягиваются из таблицы коммитов.

`GET /api/v1/practice-sessions/{session_id}/snapshots?after_id=0&through_id=123&limit=100` сохраняет форму `{snapshots: [...], has_more: bool}`. ID кадров — ID событий графа; `through_id` берётся из `graph_history_id`. Backend восстанавливает refs из изменений, а каждый кадр содержит только впервые появившиеся в нём коммиты. Frontend накапливает их при воспроизведении. Файлы и операции в исторических кадрах пустые: актуальные данные берутся из текущего состояния. Максимум 200 событий на страницу, неизвестная сессия — 404, ответы не кешируются.

Миграция `20261106_0003` переносит старые снимки в нормализованные таблицы. `20261106_0004` проверяет подтверждения, наличие коммитов и актуального состояния, затем удаляет старую `practice_snapshots`. Эти миграции требуют online-подключения для переноса данных; автоматический downgrade после нормализации не поддерживается. Применять обычной командой `alembic upgrade head`, не через autogenerate или stamp.

## Оперативная рабочая папка и индекс

`POST /api/v1/cli-worktree`: Bearer-ключ, `{session_id, generation, version, state}`; state — kind/path и files для repository. Ответ содержит только подтверждённые session_id/generation/version. Ключ и поколение кешируются при cli/connect; после перезапуска backend первый запрос проверяет прежний ключ через БД и восстанавливает кеш. Обычная отправка не создаёт сессию БД и ничего не сохраняет. Старое поколение, старая версия и конфликтующий повтор — 409; неверный ключ — 401.

`GET /api/v1/practice-sessions/{id}/worktree`: `{session_id, generation, version, state}`, state=null до первого пакета, без кеширования и без чтения БД. Отсутствующий в памяти UUID возвращает пустое состояние. `WS /ws/practice-sessions/{id}/worktree`: ready после подписки, затем `{type: "worktree_changed", worktree: {...}}` с самими данными, ping раз в 20 секунд. Медленному клиенту остаётся только последний пакет. CLI повторяет последний пакет раз в 10 секунд без увеличения версии; одинаковый повтор не публикуется.

Память и кеш допуска рассчитаны на один процесс FastAPI. Потеря оперативных данных при его перезапуске ожидаема; архив графа от этого не меняется. При приёме исторических снимков files не сохраняются даже от прежних клиентов. Текущее состояние БД возвращает files=[], frontend использует только оперативный канал для файлов.

### WebSocket от CLI

Основной оперативный транспорт CLI — `WS /ws/cli-worktree` с заголовком Authorization: Bearer. В каждом сообщении session_id/generation/version/state (только kind/path/files). Backend проверяет допуск и версию, публикует данные в браузер и отвечает `{type: "ack", session_id, generation, version}`. Конфликт/ошибка ключа возвращаются как `{type: "error", status: ...}` с закрытием 1008. POST /cli-worktree сохранён для совместимости, новый CLI его не вызывает. Наблюдение за state.json и отправка не зависят от команды; HTTP-сохранение графа остаётся отдельным каналом.

## Структура приложения

- `app/api/routes/{catalog,cli,courses,practice}/` — каталог, входящий транспорт CLI, открытие курсов и чтение практики браузером
- `app/api/schemas/{catalog,cli,courses,practice}/` — соответствующие модели запросов и ответов
- `app/db/models/courses/` — курсы и шаги; `app/db/models/practice/` — сессии, текущее состояние, коммиты и история refs
- `app/services/cli/` — присутствие и оперативные файлы; `app/services/practice/` — события и сохранение графа

Разделение каталогов не меняет URL, таблицы и формат данных. Все роутеры подключаются ровно один раз в `app/main.py`. Внутренние импорты начинаются с `app`, запуск выполняется из `backend/`


### Сервисы чтения практики

Обработчики в `app/api/routes/practice/git_practice.py` задают HTTP-параметры, заголовки и маршруты WebSocket. Чтение данных разделено на сервисы:

- `app/services/practice/practice_state.py`, класс `PracticeStateService` — текущее состояние сессии, снимок, курсор истории и присутствие CLI
- `app/services/practice/graph_history.py`, класс `GraphHistoryService` — страница истории графа и восстановление refs по событиям
- `app/services/practice/event_stream.py`, класс `EventStream` — общий WebSocket-поток для событий графа и оперативных файлов: подписка, ready, ping и завершение фоновых задач

Сервисы чтения получают отдельную AsyncSession от вызывающей ручки. Проверка существования сессии перед открытием WebSocket выполняется коротким обращением к БД; соединение БД не удерживается на время потока. URL и формат ответов при этом разделении не меняются.


### Пути HTTP-ручек CLI

Подключение, снимки и присутствие используют общий префикс `/api/v1/cli`: `POST /connect`, `POST /send-snapshot`, `POST /heartbeat`, `POST /disconnect`. CLI и тесты обращаются к этим адресам без старых алиасов. Оперативный канал файлов сохраняет отдельные адреса `/api/v1/cli-worktree` и `/ws/cli-worktree`.

`DELETE /api/v1/cli/reset-practice` принимает session_id, generation и UUID reset_id с Bearer-ключом. Сервис `PracticeResetService` блокирует сессию, очищает данные и увеличивает generation в одной транзакции без замены ключа. Ответ содержит session_id, новое generation, reset_id и reset=true. После commit обновляются оперативный допуск и присутствие CLI, публикуется state_changed. Браузер очищает кеш истории при смене поколения и перечитывает данные.

Для безопасного повтора в practice_snapshot_receipts сохраняется одно служебное подтверждение новой generation с version=0 и SHA-256 от reset_id. Это запись без снимка; входящие снимки по-прежнему начинаются с version=1. Повтор прежнего поколения с тем же reset_id возвращает результат без очистки новых данных. Другой reset_id со старым поколением отклоняется. Следующий явный сброс удаляет прежнее подтверждение. Миграция схемы не требуется.
